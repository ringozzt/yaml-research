YAML：一个反 XML 的玩笑，如何统治了云原生

YAML Ain't Markup Language — from sml-dev, 2001, to every Kubernetes cluster on Earth.

它赢的不是设计竞赛，是装机量竞赛：2001 年站在"人人恨 XML"的风口，2004 年被 Rails 带进一代 Web 程序员的日常，2014 年被 Kubernetes 加冕。它是配置格式界的 QWERTY 键盘——坑人人会背，但全世界的手指已经长成了它的形状。

01先分清：.yml 和 .yaml 是同一个东西

没有功能区别，解析器一视同仁。区别只有历史：

  • 一手官方推荐 .yaml：yaml.org 的 FAQ 自 2006 年起就明确推荐四字符后缀。
  • .yml 是 DOS/Windows 三字符扩展名限制的残留，如同 .htm 之于 .html；又被 Rails 时代的 database.yml 把习惯钉死。
  • 现状：Kubernetes 社区偏 .yaml，老牌 Ruby/CI 生态偏 .yml，两派并存至今。

名字本身也有两次人生：最初是自嘲式的 Yet Another Markup Language（"又一个标记语言"——XML 家族疯狂膨胀的年代）；2001 年底到 2002 年 4 月改成递归缩写 YAML Ain't Markup Language，刻意声明：我处理数据，不是文档标记。（Wikipedia: History and name）

02出身：2001 年，"反 XML"运动里的一封帖子

Clark Evans 在苦于 XML 写配置太啰嗦——标签噪音淹没数据本身。他想要一种"长得像人随手会写的样子"的数据格式。2001 年 5 月 11 日，他在 sml-dev 邮件列表发布 YAML Draft 0.1；这个列表本身就是从 xml-dev 分裂出来、专门研究"如何简化 XML"的。（Wikipedia / Grokipedia 复盘）

随后 Ingy döt Net（Perl 黑客）和 Oren Ben-Kiki 加入共同设计。更早的线索二手：1999 年底 Evans 已在讨论代号 "YML" 的想法，yaml.org 域名注册于 2001 年 1 月 5 日。

03设计血统：没有原创，全是借来的好零件

零件借自作用
缩进表示层级Python不用闭合标签、不用括号
纯文本序列化思路Perl 的 Data::DenterIngy 本人的模块，YAML 的直接前身之一
--- 文档分隔符MIME（RFC 2046）一个文件装多份文档
key: value 风格RFC 822 邮件头键值对的视觉习惯
转义序列C字符串字面量规则
流式读写模型SAX事件流式解析

这个拼装血统解释了它的性格：每个零件都眼熟、好上手，但拼在一起的整体语义——尤其是类型推断——没人能一眼看全。日后所有坑的种子，都埋在这里。

04版本线：1.1 埋雷，1.2 收编 JSON

版本日期关键变化
1.02004-01-29首个正式规范
1.12005-01-18功能膨胀期；布尔识别规则在这里失控
1.22009-07-21与 JSON 对齐：合法 JSON 即合法 YAML
1.2.22021-10-01现行版，勘误澄清为主

长尾事实：规范 2009 年就进了 1.2，但最流行的解析器 PyYAML 至今默认仍按 1.1 的类型规则工作——"规范说 A、解析器做 B"是这个生态的常态，写 YAML 的人必须知道自己面对的是哪个解析器。

05扩散链：三级跳登上王座

2003　Syck 进 Ruby 标准库。传奇黑客 why the lucky stiff 写的 C 解析器让 YAML 第一次有了主流语言的"户口"；Ruby 2.0 后由 Psych 接棒。一手Ruby 官方文档 History 一节
2004　Rails 的 database.yml。一代 Web 程序员对"配置文件"的肌肉记忆，是 Rails 教程给的。
2012　Ansible playbook。运维/DevOps 圈集体入坑，声明式文本配置成为运维的共同语言。
2014　Kubernetes 加冕。声明式 API 需要"写给人看的期望状态文件"：map/list/scalar 与 API 对象 1:1 对应、--- 一文件多资源、注释可写运维备注。manifest 从此默认 YAML。
2014→　生态引力期。Docker Compose、Helm、Kustomize、Argo CD、GitLab CI、OpenAPI 全面 YAML 化。
2019　GitHub Actions 改版投奔 YAML。2018 年第一版用的还是 HCL，次年推倒重来换成 YAML——最有说服力的一票：生态存量习惯赢了自研语言。二手

06为什么云原生资深程序员爱用它

真顺手的部分（对手衬托的）

  • 有注释。JSON 为数据交换而生、不支持注释——对"需要写明为什么这么配"的配置文件是硬伤；XML 有注释但标签噪音太大。
  • diff 友好。缩进即结构、无闭合标签，改一行就是一行：PR 能逐行 review，GitOps（配置即代码、Git 为唯一事实源）的工作流靠这个成立。
  • 声明式契合。K8s manifest 是"期望状态文件"，YAML 的数据导向语法与之天然同构。

没得选的部分

  • 工具链全员说 YAML：不用它，就是和 Helm、Argo、CI 以及文档里的一切示例过不去。
  • 所谓"资深偏好"，相当比例是幸存者经验：亲历过 XML 配置地狱和 JSON 无注释之痛的一代人，筛剩下的最优解就是它；同时他们知道每个坑埋在哪，并有 linter + schema 校验（kubeconform 等）兜底。

07原罪：隐式类型推断——配置文件会静默地撒谎

YAML 最大的设计债：它猜你写的值是什么类型，猜错不报错。文件合法、无异常、行为悄悄错位——这是最贵的 bug 类型。

挪威问题（The Norway Problem）

YAML 1.1 认 22 种布尔写法（y / n / yes / no / on / off 及大小写变体）。于是挪威的国家代码变成了布尔值：

country: NO        # 你想写：挪威
# 1.1 解析器读到的是：country = false

DoorDash 等公司的生产配置中过招，Kubernetes manifest、CI 配置里都有案底。二手多篇事故复盘（dev.to 等）

on: 变 true:

GitHub Actions 工作流的触发键 on，会被按 1.1 规则工作的解析器读成布尔键 true——YAML 工具链互操作史上的经典坑，与挪威问题同根。

版本号尾零蒸发

version: 1.10      # 你想写：字符串 "1.10"
# 任何解析器读到的都是：浮点数 1.1

六十进制与前导零

22:30 在 YAML 1.1 里可被读成整数 1350（22×60+30）；0644 在 1.1 是八进制 420、在 1.2 是十进制 644——同一个文件，两个数。

缓解手段只有纪律：可疑字符串一律加引号，并对配置文件做 schema 校验。YAML 1.2 已把布尔收紧为只认 true/false，但存量 1.1 解析器的行为改不了。

KYAML 的存在本身就是最强的信号：连 Kubernetes 官方都承认 YAML 的自由度是负债，但开出的药方依然是"收紧子集"，不是"迁移格式"。装机量面前，革命让位于治理。

09判断

YAML 的王座来自时间点 × 载体链：2001 年的反 XML 风口、Rails 的一代人、Ansible 的运维圈、Kubernetes 的加冕。它是配置格式界的 QWERTY——所有人都知道布局不合理，但重练手指的成本高于忍受它的成本。资深程序员爱用它，一半是真顺手（注释、diff、声明式），一半是生态引力；而"资深"本身，就包括知道那 22 种布尔写法埋在哪里。
